## What changes

ds.21 fixes one fault in how a node keeps track of the connections it accepts. Nothing else changes: no message, field, reply, price or payment rule is new, so ds.21 nodes work next to ds.20 and older nodes as ds.20 does.

### A peer that reconnects after a relay closed is answered again

- **The fault.** saorsa-transport 0.38.2 notes each connection it hands on to the rest of the node, so that a second connection from the same peer isn't handed on twice. A connection that came in through a relay endpoint was noted under the form that endpoint's socket gives an IPv4 peer, `[::ffff:a.b.c.d]:p`, and the node then noted it again under `a.b.c.d:p`. When the relay closed, only the first was cleared. From then on, every new connection from that peer's socket, direct ones too, was accepted and never handed on: no reader, no event. The peer's requests went unanswered until it came back from another port, for example after a restart.
- **The fix.** A node now notes the connections of both accept loops, its own endpoint's and a relay endpoint's, under `a.b.c.d:p`. Removing a connection clears every form of its address that no connection is noted under. A connection from an address still noted with no live connection under any of its forms is handed on in place of the one that is gone, with the INFO line `accept: <address> was announced for a connection that is gone; announcing the new one`. A second connection while one is live is still not handed on, and gets only a relay handler, as before.
- **Who noticed it.** Peers that keep one socket for a long time, such as long-running clients and other nodes, and that had reached the node through a relay at some point. Connections a node dials itself were never affected.
- **Where it comes from.** `vendor/saorsa-transport` is crates.io's saorsa-transport 0.38.2 with only this change. Its `VENDORED.md` says what changed and pins the rest, and its own tests, which the Test workflow runs, pin each part of the fix.
