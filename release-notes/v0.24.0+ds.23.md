## What changes

ds.23 is ds.22 with two robustness fixes and a set of tests that pin how payment proofs are checked. Every feature of this fork stays as it was. Nothing on the wire changes: no message is added or altered, and ds.21, ds.22 and ds.23 nodes read each other as before. No stored record, pointer, listing or paid-list entry changes format, and nothing is migrated: a ds.23 node can be rolled back to ds.22 or ds.21 on the same data folder.

### A restarted node is dialled again once it signs a newer address record

- Nodes and clients remember a failed dial of an address for 30 minutes and skip that address meanwhile; an attempt to reach the peer in which every address failed or was skipped counts as a failed dial against it. A node that restarts at the same address publishes the same addresses, so until now other nodes and long-running clients could keep skipping it for up to 30 minutes after a short restart, lowering its trust score each time they needed it, though it was back within seconds.
- A node signs a new address record only when its addresses change or when it starts; the periodic re-publication reuses the same signed record. So a ds.23 node that receives a newer signed record from a peer, whether from the peer or passed on by another peer in a lookup, clears the failures of the addresses in it and dials the peer again the next time it needs it. The record is signed by its owner, so no other peer can produce that evidence. A copy of the same record clears nothing, so re-publication can't cause repeated dials.
- A relay address whose server has been seen failing for several sessions stays suppressed until a real dial succeeds, and the 30-minute limit itself is unchanged. The change is a patch to the vendored saorsa-core (`vendor/saorsa-core/VENDORED.md`), beside the dial-order patch.
- ds.23 nodes stop skipping restarted peers of any release. Nodes of earlier releases keep the old behaviour, so they still skip a restarted ds.23 node for up to 30 minutes. Long-running clients, the gateway among them, get the fix with the next client release built on this copy.

### Requests wait their turn, as data

- A node answers storage requests with at most 64 handlers at once, and listings requests with at most 16 of their own, as before. Until now every request that arrived started a task at once, which then waited for one of those slots, first come first served: the waiting tasks had no bound, and one source sending faster than the node answers could hold every slot and make everyone else's requests, and the node's memory, grow behind it.
- Now a request waits as plain data in its topic's queue, and its handler starts only when a slot is free. The sources that have something waiting are served in turn, one request each, and each source's own requests in the order they came. A source is the address a request came from (an IPv4 address, or an IPv6 /64), since peer identities cost nothing to make. No source is capped: a source alone on a node, such as a gateway, still gets every slot.
- Each of the two queues (storage and listings) holds at most 1,000 waiting requests, the size of saorsa-core's own event buffer in front of them. At the 5 MiB wire maximum that is at most about 10 GiB of waiting requests for both together; ds.22 had no bound at all. This is the one new limit in this release. When a queue is full, the oldest request of the source with the most waiting is dropped unanswered, so a source with fewer waiting never loses a request to one with more. The node logs a warning on the first drop and each time the count doubles. A dropped request gets no answer, as requests skipped when the router falls behind get none, and its sender times out and may ask again.
- Replication between nodes has its own admission and is not affected. Answers to a node's own listings requests are taken at once, as before. The router decodes no listings message: it reads only the request id, and each message is decoded by its handler once a permit is held, so large listings messages can't hold up chunk requests.

### One-quote payment proofs stay accepted

- Nodes accept a payment proof with between one and seven quotes and check the median-priced one, as upstream does. This release changes nothing there; it adds tests that fail if a later merge brings in a minimum number of quotes.
- The reason: upstream rejects a minimum on purpose (its ADR-0006), this fork's client pays with as few as one witnessed quote when fewer nodes can be used, and every node from ds.19 on, ds.21 and ds.22 included, passes records to other nodes with slim proofs that normally hold one quote. A minimum would refuse honest uploads and all replication between releases.
- A proof with one quote lets a node near an address pay itself for storing a record there, at the cost of gas, as on upstream's network. Whether that should change is an open decision; a change would be to how payments are split between nodes, not to this check.

### Releases are signed by this repository's own tool

- The archive nodes install is signed as before (ML-DSA-65, the same key, the same check by every node). The release workflow now signs it with `release-sign`, built from this repository, instead of downloading upstream's ant-keygen, which stopped being available on 14 November 2026.
- To check a release yourself: build `release-sign` from the release's source (`cargo build --release --locked --bin release-sign`) and run `release-sign verify --key release-signing-key.pub --input ant-node-cli-linux-x64.tar.gz --signature ant-node-cli-linux-x64.tar.gz.sig`. ant-keygen 0.1.0's `verify` accepts the same files.
