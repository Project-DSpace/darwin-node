## What changes

ds.22 brings in upstream's node release 0.24.0. Every feature of this fork stays as it was: DARWIN payments and the price curve, size-priced records and root payments, merkle payments refused, the payment check's RPC fallback and deadline, erasure only under disk pressure with possession proven first, full-not-faulty, paged neighbour sync, listings, slim proofs, direct-first dialling, the relay switch, the browser limits, and releases from this repository signed with its key. No stored record, pointer, listing or paid-list entry changes format, and nothing is migrated: a ds.22 node can be rolled back to ds.21 on the same data folder.

### Get-or-closer (upstream's ADR-0020): answered, not yet announced

- A node now answers a new chunk request, get-or-closer: it returns the chunk when it holds it, and otherwise the peers nearer to it that a FIND_NODE would name, so a client finds a chunk in fewer steps. The chunk is read as a GET reads it: a stored file whose bytes don't match its name is removed rather than served, and replication restores it.
- ds.22 nodes do not announce the request in their user agent, though upstream's nodes do (with `get-or-closer/1` after the version). A ds.22 node's agent has ds.21's form with the new version. The reason: nodes before ds.22 read a peer's whole agent as its release, so they would read an announcing node as no release at all, send it single neighbour-sync messages instead of pages, and charge it for their slow answers. The mixed-version harness showed those charges on 14 November 2026, and the token was held back that day (a decision Claude made under Dan's instructions for this merge, which include "do not risk our data").
- ds.22 is the first release that reads only the first word of a peer's agent, so the token can be turned on in a later release once no node before ds.22 is left on the network.
- Until then clients read ds.22 nodes with FIND_NODE and GET, as they read nodes today; a client built on upstream's 0.3.13 sends get-or-closer only to nodes that announce it.
- Browsers can't use the request, and the browser listener refuses it, as upstream intends. Nodes never send it to each other.

### Other changes from upstream

- The browser listener can ask a home router to forward its port (UPnP, upstream's ADR-0027) when it chooses its own public address. Our servers' image always names the address, which turns this off.
- The browser listener logs a summary every five minutes (`webrtc listener summary (cumulative)`), with how long GETs took to serve and to wait for room, beside the refusal counts it already logged.
- A responsible-chunk audit now samples only the records a node is in range for, so the records it keeps out of range no longer use up its sample. It charges fewer peers, never more.
- The storage audit's verdict is shared with upstream's tests of known attacks, so those tests run the code that ships; the seen-holder record behind the full-node waiver is still written only from a real audit.
- ant-protocol 6.0.0, saorsa-core 0.30.0 and saorsa-transport 0.39.0, each still vendored with our changes (`vendor/*/VENDORED.md`), and darwin-listings moved to ant-protocol 6.0.0 with no source change. saorsa-transport 0.39.0 fixes a deadlock in its connection driver and starts a browser's encrypted session sooner.
- Security updates: tokio 1.53.3, rustls 0.23.46, rustls-webpki 0.103.16, and zip 9 (used only on Windows).

### What is not taken from upstream 0.24.0

- **Upstream's new rules for erasing records (ADR-0028).** Upstream rewrote the same part of the node our nodes have run since ds.11 and ds.17: erasure only when the disk is short of room, farthest records first, each after the nodes now nearest prove they hold it, with the falling floor, free inodes counted, two phases, and the paid list's size classes. Taking upstream's version would have replaced that design and stopped recording size classes, so ds.22 keeps ours unchanged.
- **Upstream's larger browser limits.** The listener keeps 128 sessions, 256 channels and 16 request slots by default.
- Upstream's build-script and CI changes, which ours replace.

### During the rollout

ds.21 and ds.22 nodes read each other's user agents, so they page neighbour sync to each other in both directions and send each other "full" notices, as nodes of one release do. Every release reads every message ds.22 sends.

## Updating the image (Docker)

Nothing to do. The nodes install ds.22 by themselves.
